# Функциональное программирование и промежуточные состояния

Для ответа я взял свой проект
[«Электронный журнал»](main.py). В нём хранятся студенты, учебные курсы и
оценки, а также вычисляется средний балл.

## 1. Где можно отказаться от промежуточных результатов

В методе `student_average()` оценки сначала собираются в изменяемый список:

```python
grades = []

for course in self._courses.values():
    grades.extend(course.student_grades(student_id))

return sum(grades) / len(grades)
```

Список `grades` нужен только для последующего вычисления. Его можно не хранить,
а сразу передавать оценки по цепочке вычислений:

```python
grades = (
    grade
    for course in self._courses.values()
    for grade in course.student_grades(student_id)
)
```

Однако для среднего значения всё равно одновременно нужны сумма и количество
оценок. Поэтому удобнее написать чистую функцию, которая получает оценки и
возвращает результат, не изменяя данные журнала:

```python
def calculate_average(grades):
    grades = tuple(grades)
    return None if not grades else sum(grades) / len(grades)
```

После этого методы `student_average()` и `course_average()` смогут только
подготавливать последовательность оценок и передавать её в одну общую функцию.
Так логика вычисления не дублируется и не имеет побочных эффектов.

Ещё один источник изменяемого состояния — методы `add_student()`,
`add_course()` и `add_grade()`. Сейчас они изменяют уже существующий объект
журнала. В более функциональном варианте функция добавления оценки могла бы
принимать журнал и возвращать **новый** журнал с добавленной оценкой. Старый
объект при этом оставался бы без изменений. Это потребует больше памяти, зато
каждый результат будет предсказуемым, его проще тестировать и безопаснее
использовать параллельно.

Я понял, что отказываться нужно не от всех локальных переменных. Переменная,
которая один раз получила значение и больше не изменяется, часто делает код
понятнее. Основная проблема — изменяемые промежуточные состояния, глобальные
переменные и функции со скрытыми побочными эффектами.

## 2. Архитектура без явного хранения промежуточных состояний

Такую систему можно представить как конвейер преобразований:

```text
входные данные → проверка → преобразование → вычисление → результат
```

Каждый этап получает значение на вход и возвращает новое значение на выход.
Функция не изменяет входные данные и не зависит от глобальных переменных.
Благодаря этому результат функции определяется только её аргументами.

Например, добавление оценки в журнал можно разбить на следующие этапы:

1. Получить команду с идентификатором студента, названием курса и оценкой.
2. Проверить существование студента и курса, а также допустимость оценки.
3. На основе прежнего состояния создать новое состояние журнала.
4. Вычислить средние значения из нового состояния.
5. Сформировать отчёт и передать его на вывод.

Постоянные данные всё равно должны где-то находиться, например в базе данных.
Но внутри одной операции не обязательно хранить множество изменяемых
промежуточных объектов. Система загружает исходные данные на границе программы,
пропускает их через цепочку чистых функций и сохраняет только конечный
результат.

Ввод с клавиатуры, запись в файл, работа с базой данных и печать отчёта являются
побочными эффектами. Их лучше отделять от вычислительной логики и выполнять
только на границах программы. Тогда основная часть приложения остаётся
предсказуемой: её можно проверять простыми тестами без настоящей консоли или
базы данных.

Таким образом, архитектура может состоять из двух частей:

- функциональное ядро — проверяет и преобразует неизменяемые данные;
- внешняя оболочка — получает данные, вызывает функции ядра и сохраняет или
  выводит окончательный результат.

Полностью избавиться от хранения состояния в реальной сложной системе обычно
нельзя, но можно сделать его явным, неизменяемым внутри вычислений и
сосредоточенным в небольшом количестве хорошо контролируемых мест.
